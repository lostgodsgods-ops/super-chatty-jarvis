Before proposing or implementing product changes, read **[SUPER_CHATTY_JARVIS_MASTER_SPEC.md](SUPER_CHATTY_JARVIS_MASTER_SPEC.md)**. Treat it as a living specification, not proof that every listed capability already exists. When the owner approves new recommendations, update the specification and implementation plan as appropriate.

## Mission

Explore and incrementally build a secure, owner-controlled, extensible AI collaboration platform for knowledge research, task planning, voice-first interaction, persistent memory, specialized agents, robotics learning, finance-system design, quantum-computing research, and approved automation. The long-term direction is AGI-like capability research; do not claim that true AGI has been achieved without rigorous evidence.

## Collaboration request

AI agents, developers, and researchers may suggest:
1. Practical architecture and open standards for agent-to-agent communication.
2. Modular plugins and integration paths for new owner recommendations.
3. Safe, affordable tools for robotics simulation and knowledge retrieval.
4. Secure AI-provider, GitHub, Cloudflare, task-queue, memory, and audit integrations.
5. Dynamic creation of task-specific agents with owner approval and least-privilege permissions.
6. Banking/finance and Chaticoin wallet designs kept non-live or sandbox/testnet until separately authorized and properly supported.
7. Quantum-computing research integrations using real, available services.
8. Security, privacy, compatibility, testing, and rollback improvements.

## Boundaries

Do not assume access to private accounts, credentials, funds, devices, or systems. Never expose secrets in source code, frontend bundles, prompts, or logs. Do not let agents self-grant permissions or bypass the SecurityGate. Require explicit owner approval for consequential actions such as repository writes, merges, production deployments, destructive migrations, external messages, financial transactions, or sensitive hardware control.

Prefer finding a safe, feasible implementation path for new recommendations instead of rejecting them unnecessarily. Verify compatibility and run appropriate tests before merging. Report blockers honestly when a dependency, permission, external API, safety constraint, or technical limitation prevents implementation.

## Evidence and status

Report actual results using PASS / FAIL / BLOCKED / NOT TESTED. Distinguish PROPOSED, AVAILABLE, CONFIGURED, TESTED, ENABLED, and VERIFIED. Never claim a feature is implemented, merged, deployed, or operational without corresponding evidence. Direct model tests or successful deployment commands alone do not prove end-to-end functionality.
